Roteiro de auditoria e entrega — CondoGestor V2
Escopo didático a partir das aulas 09–16 de Laboratório de Programação (2026.2). Os exemplos do professor usam Chamado, Cliente e Tag, mas aqui a aplicação real é o CondoGestor. Cada tópico indica um conceito a demonstrar de forma coerente no projeto — não é exigência automática de copiar cada exemplo/sugestão do slide. Não é uma rubrica formal de pontuação da prova.
Como usar este roteiro
Inspecione o estado ATUAL do repositório no VS Code: git status, pom.xml, Models, Repositories, Services, Controllers, templates e configuração.
Para cada linha abaixo, registre FEITO / PARCIAL / FALTA / DEPENDE DE CONFIRMAÇÃO, a evidência (arquivos/métodos) e o menor ajuste necessário.
O ZIP usado para preparar este documento era anterior a algumas alterações locais recentes. Já foram iniciadas validações de nome na criação e edição de Morador; confirme no workspace atual antes de reescrever.
Priorize correções funcionais para demonstração da V2. Evite ampliar o produto com módulos não pedidos.
Faça um relatório final com o checklist atualizado, testes executados, limitações e passos manuais restantes.
Conteúdos das aulas e evidências a buscar

Aula 09 — Objetos e formulários. Entidades/objetos em Java, GET para abrir formulário, POST para receber objeto, th:object, th:field, th:each e redirecionamento após sucesso. Usar Moradores, Ocorrências ou Reservas; não recriar persistência temporária em List se o banco já existe.

Aula 10 — Identificação e rotas dinâmicas. IDs nos registros, @PathVariable, visualização de dados por ID e exclusão por POST, com tratamento de registro inexistente e autorização/associação ao condomínio.

Aula 11 — CRUD e feedback. Criar, listar, consultar, atualizar, excluir; mensagens de êxito/erro com RedirectAttributes e exibição no Thymeleaf onde realmente fizer sentido. Verificar fluxos existentes antes de adicionar rotas.

Aula 12 — JPA, entidades e migrations. Conferir @Entity, @Id, @GeneratedValue, tabelas, colunas e relacionamentos com o PostgreSQL. O slide também ensina Flyway e ddl-auto=validate; a aplicação antiga usa ddl-auto=update e script SQL avulso. Não mudar o banco existente automaticamente. Propor estratégia segura e solicitar autorização se migrations reais forem necessárias.

Aula 13 — Repositories e persistência. Conferir interfaces que estendem JpaRepository, operações save/findAll/findById/deleteById, persistência após reinício e buscas corretamente restritas ao condomínio.

Aula 14 — Validação no backend. spring-boot-starter-validation, @NotBlank, @Size, @Email quando apropriado, @Valid, BindingResult, mensagens com th:errors, retorno ao formulário com dados preenchidos e bloqueio do save quando inválido. Aplicar ao cadastro E à edição; não confiar apenas no HTML/JS.

Aula 15 — Service e regras de negócio. Manter operações e regras da aplicação nos Services, especialmente status inicial, transições de status, vínculos e validações de operação; Controller decide HTTP/template/feedback, Repository persiste. Não criar Service que só repasse métodos mecanicamente quando isso não agregue valor.

Aula 16 — Relacionamentos JPA. Verificar cardinalidade real (@ManyToOne, @OneToMany quando necessário, associação com @JoinColumn), formulários de seleção de entidades existentes, FK e coerência do banco. O slide apresenta @ManyToMany/@JoinTable como outro conceito; avaliar aplicabilidade no domínio, sem inventar Tag ou associação artificial.
Ordem de trabalho sugerida (a validar na auditoria)
0 — Preflight e segurança

Ler as alterações locais recentes, sem descartá-las.

Verificar se a aplicação inicia e se o fluxo do banco funciona com configuração já existente, sem revelar segredos.

Investigar credenciais hardcoded/fallback e indicar procedimento de rotação. Não fazer push de segredos ou assumir que um novo commit limpa o histórico.
1 — Funcionalidades demonstráveis e validação (prioridade alta)

Confirmar CRUD atual de Moradores e operação de Ocorrências/Reservas.

Completar validação no backend de campos obrigatórios e formato, incluindo cadastro/edição e feedback visível.

Tratar IDs inexistentes e preservação dos dados nos formulários com erro.

Adicionar/ajustar flash messages nas operações que exigem feedback.
2 — Regras de negócio e relacionamentos (prioridade alta)

Conferir Services vs Controllers, status, conflitos de reserva e relações entre entidade/condomínio.

Verificar se operações não aceitam associação com registros de outro condomínio.

Conferir JPA, cardinalidades e persistência real. Evitar recursos extras sem ganho didático.
3 — Migrations / Flyway (requer avaliação e aprovação)

Apresentar diferenças entre banco atual e estratégia ensinada nos slides.

Se decidido usar Flyway: elaborar migração/baseline preservando dados; validar em ambiente isolado antes do banco compartilhado.

Não rodar SQL de alteração, ddl-auto=create/create-drop ou mudança de schema no Neon compartilhado sem aprovação.
4 — Validação final e entrega

Executar os testes/compilação realmente disponíveis. Informar quando faltarem ferramentas locais.

Testar no navegador cenários válidos/inválidos, navegação, feedback, CRUD, persistência e dados de cada condomínio.

Verificar git diff --check, git status e arquivos que entrariam no commit.

Atualizar documentação relevante para refletir o backend atual, sem apagar histórico útil da V1.

Produzir quadro final de evidências: aula → funcionalidade do CondoGestor → classe/rota/template → teste → situação.
Regras de parada
Pare e peça aprovação antes de: alterar schema de banco compartilhado; executar SQL destrutivo; expor/alterar credenciais reais; criar módulos fora do escopo; reescrever arquitetura ou migrar versões principais de Java/Spring; fazer git push ou --force.

### Verificações efetuadas

- `git diff --check` sem erros de espaço em branco.
- `node --check src/main/resources/static/js/script.js` sem erro de sintaxe.
- Compilação dos fontes com `javac -source 8 -target 8`, usando as dependências já presentes no cache local: concluída sem erros. Os avisos vêm do JDK 21 local ao direcionar bytecode Java 8 e de uma API já depreciada em `SecurityConfig`.
- Não há Maven nem Maven Wrapper neste checkout e não há testes em `src/test`; testes Spring e o fluxo com o PostgreSQL não foram executados.

### Segurança e banco

- A configuração atual possui parâmetros diretos de conexão/autenticação. Eles não foram copiados, alterados nem executados; recomenda-se rotacioná-los se já estiverem no histórico do repositório e movê-los para variáveis de ambiente em uma tarefa aprovada separadamente.
- `SecurityConfig` mantém `anyRequest().permitAll()` e CSRF desabilitado; os Controllers fazem a checagem manual de `usuarioLogado`. Isso é suficiente apenas para a demonstração atual e deve ser tratado como pendência de segurança, não como autorização completa.
- Nenhuma migration, script SQL, alteração de schema, operação destrutiva, commit ou push foi executado.
